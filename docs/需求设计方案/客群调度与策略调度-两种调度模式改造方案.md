# 客群调度与策略调度——两种调度模式改造方案

> 文档版本：V1.0  
> 日期：2026年6月  
> 状态：方案设计（待实施）

---

## 一、需求背景

### 1.1 当前现状

客群调度和策略调度当前仅支持一种模式：审批通过后直接同步IOP/网格通，接收人无确认环节，无法区分"省公司统一执行"和"按地市分别执行"两种业务场景。

### 1.2 核心痛点

1. **无领单确认**：审批通过后直接推送IOP，接收人可能不在线或不认可，导致IOP侧垃圾数据堆积
2. **无法按区域分配**：所有圈选区域的客户合并成一个文件，无法按区域分别指定不同接收人
3. **缺乏执行反馈**：推送到IOP后无法追踪IOP活动策划和执行进展，形成信息黑洞

### 1.3 改造目标

1. 支持两种调度模式：本级调度（统一执行）和下级调度（按区域分发执行）
2. 增加领单确认机制，确保"有人接、有人做"
3. 建立IOP进展双向联动，在市场运营平台可追踪IOP活动全流程

## 二、两种调度模式定义

| 模式 | 定义 | 适用场景 | 工单拆分 | 客户清单 |
|------|------|---------|---------|---------|
| 本级调度 | 由发起人同级区域的IOP/网格通人员统一接收和执行 | 统一策划、统一执行的集中式营销 | 主单不拆分，1个主接收人 | 1个总文件（所有圈选区域的客户合集） |
| 下级调度 | 按圈选区域的下级区域分别指定接收人，各自执行 | 统一圈选、差异化执行的分布式营销 | 主单按区域拆分子单，每个子单1个主接收人 | 每个区域1个客户清单文件 |

### 2.1 行业实践依据

| 模式 | 典型场景 | 行业实践依据 |
|------|---------|------------|
| 本级调度 | 省公司市场部圈选全疆高端客户，统一策划"全球通尊享权益升级"活动，由省公司IOP运营人员统一策划执行 | 中国移动集团"集中运营"模式，省公司集中策划+统一执行，确保品牌一致性和资源效率 |
| 下级调度 | 省公司圈选16地市潜在流失客户，但各地市竞争态势、客户偏好差异大，需各地市IOP人员分别策划差异化方案 | 中国移动"省专地协"模式，省公司统一圈选+地市差异化执行，兼顾规模效应和本地化灵活度 |

## 三、完整业务流程

### 3.1 本级调度 + IOP 流程

```
步骤1: 发起人圈选标签+区域 → 进入调度派发页
步骤2: 选择派发系统=IOP → 选择调度模式=本级调度
步骤3: 选择IOP主接收人（仅1人，同级区域人员）
        · 区公司发起 → 选择区公司IOP人员
        · 地州公司发起 → 选择本地区IOP人员
步骤4: 填写工单信息 → 提交审批
步骤5: 审批人审批通过
        ┌─────────────────────────────┐
        │ 工单状态变为：待领单           │
        │ 系统执行3项通知：              │
        │  ① 平台待办（需处理操作）       │
        │  ② 站内消息（通知提醒）         │
        │  ③ 短信（保证触达）            │
        └─────────────────────────────┘
步骤6: 接收人在市场运营平台领单确认
        · 点击"领单"→ 工单状态变为：已领单
        · 超时机制：24h未领单→催办，72h未领单→标记异常
步骤7: 领单后，系统同步工单信息+客户清单文件至IOP
        · 调用IOP接口：客群实时同步（6.1.1）
        · SFTP传输：客户明细文件（1个总文件）
步骤8: 接收人登录IOP，基于同步的客群创建活动策划
步骤9: IOP推送活动策划进展至市场运营平台
        · 活动创建 → 工单状态：IOP策划中
        · 活动审批通过 → 工单状态：IOP策划中（审批通过）
        · 活动开始执行 → 工单状态：IOP执行中
        · 执行进度更新 → 工单状态：IOP执行中（进度更新）
        · 活动结束 → 工单状态：执行完成
步骤10: IOP触客结果回传（6.1.3）→ 工单状态：待评估
步骤11: 市场运营平台后评估（如已开启）→ 工单状态：已关闭
```

### 3.2 下级调度 + IOP 流程

```
步骤1: 发起人圈选标签+区域 → 进入调度派发页
步骤2: 选择派发系统=IOP → 选择调度模式=下级调度
步骤3: 按下级区域选择IOP主接收人
        · 每个下级区域必填1个主接收人
        · 可选填协同接收人（多人）
        · 示例：圈选了乌鲁木齐、克拉玛依、昌吉
          → 乌鲁木齐主接收人：张三（区公司IOP）
          → 克拉玛依主接收人：李四（克拉玛依IOP）
          → 昌吉主接收人：王五（昌吉IOP）
步骤4: 填写工单信息 → 提交审批
步骤5: 审批人审批通过
        ┌─────────────────────────────────────┐
        │ 系统自动按区域生成子单：                │
        │  主单 IND-20260605-001              │
        │  ├─ 子单 IND-20260605-001-01 (乌鲁木齐) │
        │  ├─ 子单 IND-20260605-001-02 (克拉玛依) │
        │  └─ 子单 IND-20260605-001-03 (昌吉)    │
        │                                      │
        │ 每个子单独立推送通知给对应接收人：        │
        │  ① 平台待办                           │
        │  ② 站内消息                           │
        │  ③ 短信                              │
        │                                      │
        │ 主单状态变为：执行中（子单待领单）        │
        │ 子单状态变为：待领单                    │
        └─────────────────────────────────────┘
步骤6: 各区域接收人分别领单确认
        · 每个子单独立领单，互不影响
        · 子单领单后状态：已领单
        · 超时机制同本级调度
步骤7: 各子单领单后，系统分区域同步
        · 调用IOP接口：仅同步该区域的客群信息（6.1.1，按区域过滤）
        · SFTP传输：该区域的客户明细文件（每个子单独立1个文件）
步骤8: 各区域接收人分别登录IOP，创建各自的活动策划
步骤9: IOP推送各区域活动策划进展
        · 每个子单独立跟踪IOP进展
        · 状态流转同本级调度步骤9
步骤10: IOP触客结果按区域回传 → 各子单状态：待评估
步骤11: 所有子单完成后，主单汇总 → 主单状态：待评估
步骤12: 后评估 → 主单/子单状态：已关闭
```

### 3.3 本级调度 + 网格通 流程

```
步骤1~4: 同本级调度+IOP，但选择派发系统=网格通
步骤3: 选择执行角色（地市集运/网格经理），选择1个主接收人
步骤5: 审批通过
        ┌─────────────────────────────────┐
        │ 无领单确认环节                    │
        │ 直接推送任务至网格通：              │
        │  · 调用网格通任务推送接口(6.2.1)    │
        │  · SFTP传输客户明细文件(1个总文件)   │
        │  · 推送平台待办+站内消息+短信        │
        │                                  │
        │ 工单状态变为：执行中                │
        └─────────────────────────────────┘
步骤6: 网格通推送执行进度回传（6.2.3）
        · 工单状态实时更新
步骤7: 执行完成 → 工单状态：待评估
步骤8: 后评估 → 工单状态：已关闭
```

### 3.4 下级调度 + 网格通 流程

```
步骤1~4: 同下级调度+IOP，但选择派发系统=网格通
步骤3: 按下级区域选择接收人+执行角色
步骤5: 审批通过
        ┌──────────────────────────────────────┐
        │ 系统按区域生成子单（同下级调度+IOP）     │
        │ 无领单确认环节                         │
        │ 直接推送各区域任务至网格通：              │
        │  · 按区域调用网格通任务推送接口           │
        │  · SFTP传输各区域客户明细文件            │
        │  · 各子单推送平台待办+站内消息+短信       │
        │                                       │
        │ 主单状态：执行中                         │
        │ 子单状态：执行中                         │
        └──────────────────────────────────────┘
步骤6: 网格通按区域回传执行进度 → 各子单状态实时更新
步骤7: 所有子单执行完成 → 主单状态：待评估
步骤8: 后评估 → 已关闭
```

## 四、领单超时机制

审批通过后不应直接同步IOP，需接收人领单确认后再同步。但领单必须有超时机制，防止工单永远卡在"待领单"状态。

| 超时阶段 | 时限 | 动作 |
|---------|------|------|
| 首次领单 | 24小时 | 未领单→自动催办（站内消息+短信再推一次） |
| 二次催办 | 再24小时 | 仍未领单→升级通知派发人，派发人可决定：重新指定接收人 / 延长等待 / 强制关闭 |
| 催办上限 | 3次（72小时） | 仍未领单→工单自动标记"领单超时"，状态变为"异常"，由派发人处理 |

## 五、工单状态流转改造

### 5.1 当前状态流转（6种调度通用）

```
草稿 → 待审批 → 审批中 → 审批通过 → 执行中 → 已完成
                                    ↓
                                  已驳回（退回修改）
```

### 5.2 改造后主单状态流转

```
草稿 → 待审批 → 审批中 → 审批通过
                         ↓
              ┌──────────┼──────────────┐
              ↓          ↓              ↓
         [本级调度]  [下级调度]    [审批驳回]
              ↓          ↓              ↓
         待领单     执行中(子单进行)   已驳回
              ↓          ↓
         已领单     执行中(子单进行)
              ↓          ↓
         IOP策划中   (子单独立流转)
              ↓          ↓
         IOP执行中        ↓
              ↓          ↓
         执行完成    执行完成(全部子单完成)
              ↓          ↓
         待评估      待评估
              ↓          ↓
         已关闭      已关闭
```

### 5.3 子单状态流转（仅下级调度+IOP时有）

```
待领单 → 已领单 → IOP策划中 → IOP执行中 → 执行完成 → 待评估 → 已关闭
    ↓
  领单超时(异常)
```

### 5.4 子单状态流转（仅下级调度+网格通时有）

```
执行中 → 执行完成 → 待评估 → 已关闭
```

### 5.5 新增状态枚举

| 状态 | 含义 | 适用场景 |
|------|------|---------|
| 待领单 | 审批通过，等待接收人确认 | IOP模式（本级+下级子单） |
| 已领单 | 接收人已确认领单，待同步IOP | IOP模式（本级+下级子单） |
| IOP策划中 | 接收人已在IOP创建活动 | IOP模式 |
| IOP执行中 | IOP活动开始触达客户 | IOP模式 |
| 领单超时 | 接收人72h未领单 | IOP模式（异常状态） |

### 5.6 工单状态徽章颜色

| 状态 | 颜色 | 说明 |
|------|------|------|
| 待领单 | 橙色 | 需要接收人操作 |
| 已领单 | 蓝色 | 等待IOP同步 |
| IOP策划中 | 紫色 | IOP活动策划中 |
| IOP执行中 | 主题色 | IOP活动执行中 |
| 领单超时 | 红色 | 异常状态，需处理 |

## 六、派发页UI改造方案

### 6.1 调度模式选择（新增控件）

**位置**：派发配置区域，"派发系统"选择IOP/网格通之后，新增"调度模式"选择。

**规则**：

| 派发系统 | 调度模式选项 | 默认值 |
|---------|------------|-------|
| IOP | 本级调度 / 下级调度 | 本级调度 |
| 网格通 | 本级调度 / 下级调度 | 下级调度 |

**UI形式**：Radio按钮组，与派发系统选择样式一致。

**选择逻辑**：
- 选择"本级调度"→ 接收人选择区域显示"选择1名同级IOP接收人"
- 选择"下级调度"→ 接收人选择区域变为"按区域指定接收人"表格

### 6.2 本级调度 - IOP接收人选择（改造现有控件）

**现有**：一个IOP处理人选择弹窗，从列表中选1人。

**改造**：
- 弹窗中的人员列表需按"同级区域"过滤
  - 区公司发起 → 只显示区公司IOP人员
  - 地州公司发起 → 只显示本地区IOP人员
- 人员列表增加"所属区域"列，便于确认
- 仍然只选1人

### 6.3 下级调度 - IOP接收人选择（新增控件）

**UI形式**：表格，每行一个圈选区域，每行一个"选择接收人"按钮。

| 圈选区域 | 主接收人 | 协同接收人 | 操作 |
|---------|---------|----------|------|
| 乌鲁木齐 | 张三（区公司IOP） | — | 选择 / 更换 |
| 克拉玛依 | 李四（克拉玛依IOP） | — | 选择 / 更换 |
| 昌吉 | 未选择 | — | 选择 |

**选择弹窗**：点击"选择"→ 弹出该区域所属IOP人员列表（从列表中选1人为主接收人）。

**校验规则**：
- 每个圈选区域必须选择1个主接收人，否则不可提交
- 提交时统一校验，未选区域高亮提示

### 6.4 下级调度 - 网格通接收人选择

与IOP类似，但替换为：
- 执行角色（地市集运/网格经理）
- 每个区域的网格通人员列表

## 八、IOP对接接口改造

### 8.1 客群实时同步接口（6.1.1 改造）

| 项目 | 改造前 | 改造后 |
|------|-------|-------|
| 调用时机 | 审批通过后立即调用 | **领单确认后**才调用（本级调度）；各子单领单确认后分区域调用（下级调度） |
| 请求参数 | 全量客群信息 | 本级调度=全量；下级调度=仅该区域客群信息（新增areaCode过滤参数） |
| 同步频率 | 1次 | 本级调度=1次；下级调度=每个领单子单各1次 |

### 8.2 客群明细SFTP（6.1.2 改造）

| 项目 | 改造前 | 改造后 |
|------|-------|-------|
| 文件数量 | 1个总文件 | 本级调度=1个总文件；下级调度=每个子单1个文件 |
| 文件命名 | `{工单号}_客户清单.csv` | 本级调度=`{工单号}_客户清单.csv`；下级调度=`{工单号}_{区域编码}_客户清单.csv` |
| 传输时机 | 审批通过后 | 领单确认后（与6.1.1同步调用时机对齐） |
| SFTP目录 | `/upload/{工单号}/` | 本级调度=`/upload/{工单号}/`；下级调度=`/upload/{工单号}/{区域编码}/` |

### 8.3 活动策划进展回调接口（新增）

| 项目 | 定义 |
|------|------|
| 接口方向 | IOP → 市场运营平台（webhook回调） |
| 接口地址 | `POST /api/iop/activity/progress-callback` |
| 请求参数 | 见下方 |

```json
{
  "eventType": "ACTIVITY_CREATED | ACTIVITY_APPROVED | ACTIVITY_STARTED | ACTIVITY_PROGRESS | ACTIVITY_COMPLETED",
  "eventTime": "2026-06-10T14:30:00+08:00",
  "ticketNo": "COD-20260605-001",
  "subTicketNo": "COD-20260605-001-01",
  "activityId": "IOP-ACT-20260610-001",
  "activityName": "全球通尊享权益升级-乌鲁木齐",
  "operator": "张三",
  "progressData": {
    "targetCount": 5000,
    "reachedCount": 3200,
    "reachedRate": 0.64,
    "successCount": 2100,
    "failCount": 1100
  }
}
```

**MVP阶段支持的事件类型**：

| eventType | 说明 | 必须支持 |
|-----------|------|---------|
| ACTIVITY_CREATED | IOP活动创建 | 是 |
| ACTIVITY_APPROVED | IOP活动审批通过 | 否（可后续迭代） |
| ACTIVITY_STARTED | IOP活动开始执行 | 是 |
| ACTIVITY_PROGRESS | IOP活动执行进度更新 | 否（可后续迭代） |
| ACTIVITY_COMPLETED | IOP活动结束 | 是 |

### 8.4 领单确认接口（新增）

| 项目 | 定义 |
|------|------|
| 接口方向 | 前端 → 市场运营平台后端 |
| 接口地址 | `POST /api/dispatch/ticket/claim` |
| 请求参数 | `{ "ticketNo": "COD-20260605-001", "subTicketNo": "COD-20260605-001-01" }` |
| 业务逻辑 | ① 更新工单状态：待领单→已领单 ② 调用6.1.1同步客群信息至IOP ③ 触发6.1.2 SFTP传输客户清单 ④ 推送站内消息给派发人："XXX已领单" |

## 九、消息通知机制

### 9.1 通知事件清单

| 事件 | 通知对象 | 通知渠道 | 消息内容模板 |
|------|---------|---------|------------|
| 审批通过（待领单） | 主接收人（本级）/ 各区域接收人（下级） | 待办+消息+短信 | "您有1条新的调度工单待领单：{工单号}-{工单标题}，请尽快处理" |
| 领单成功 | 派发人 | 消息 | "{接收人}已领单确认：{工单号}-{工单标题}" |
| 领单超时24h（催办） | 接收人 | 消息+短信 | "提醒：您有1条调度工单尚未领单：{工单号}-{工单标题}，请尽快处理" |
| 领单超时72h（升级） | 派发人 | 待办+消息+短信 | "预警：工单{工单号}领单超时，接收人{姓名}72小时内未确认，请处理" |
| IOP活动创建 | 派发人 | 消息 | "IOP活动已创建：{活动名称}，关联工单{工单号}" |
| IOP活动开始执行 | 派发人 | 消息 | "IOP活动开始执行：{活动名称}，关联工单{工单号}" |
| IOP活动完成 | 派发人 | 待办+消息 | "IOP活动执行完成：{活动名称}，关联工单{工单号}，请查看触客结果" |

### 9.2 领单超时检测机制

| 项目 | 定义 |
|------|------|
| 检测方式 | 后端定时任务（cron），每30分钟扫描一次 |
| 扫描条件 | 工单状态=待领单 且 领单创建时间<当前时间-24h |
| 催办次数上限 | 3次（第1次24h，第2次48h，第3次72h） |
| 第3次催办后 | 标记工单为"领单超时"，通知派发人 |
| 派发人操作 | 可重新指定接收人（生成新的领单待办）或强制关闭工单 |
