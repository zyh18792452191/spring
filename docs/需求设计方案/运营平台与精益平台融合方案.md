# 运营平台与精益平台融合方案

> 编制依据：精益平台操作手册、接口文档、现状梳理PPT、流程梳理PPT、常用页面清单、4A单点登录接口文档、运营平台现有功能
> 编制原则：逐一分析、有据可查、可落地实施

## 一、背景与目标

### 1.1 融合背景

**业务痛点**：在市场运营平台建设上线之后使用人员需要在市场运营平台、精益平台两套系统之间频繁切换——

- 精益平台处理预警工单的创建、审批、派发、执行反馈
- 运营平台查看指标数据、进行指标/策略/客群调度、商机分析、区域攻坚调度

两套系统界面风格不同、登录入口不同、数据不互通，导致：

1. **操作效率低**：需在两个系统分别操作
2. **流程割裂大**：指标/策略/客群/区域攻坚/商机调度等在运营平台，预警调度等在精益平台，无法形成"指标→预警→调度→执行→效果"在同一平台的完整闭环
3. **学习成本高**：需要学习两套系统的操作逻辑

**政策驱动**：基于集团规范，需建设"XX移动市场运营平台"，包括平台的命名、菜单结构、界面框架均需与集团规范保持统一，精益平台目前有多项不一致，需要与市场运营平台进行融合。

### 1.2 核心目标

**将运营平台作为统一入口，分阶段将精益平台的核心能力融合至运营平台，最终实现"一个平台、一套界面、一次登录、闭环运营"。**

具体目标：

1. **统一用户界面和使用体验**：用户只需登录运营平台，即可完成所有市场运营相关操作
2. **统一调度体系**：以运营平台调度中心为基础，扩展支持精益平台的预警和看管场景
3. **统一数据通路**：运营平台直接对接外部系统，不经精益平台中转
4. **对齐集团规范**：融合后的能力按集团规范验收，不迁就精益平台现有实现

### 1.3 分步实施的必要性

方案需体现阶段性成果，如果无法一步到位，可以分步实施。以下说明无法一步到位的原因：

1. **业务连续性要求**：精益平台日均处理数百条预警工单，任何迁移都不能中断在途工单的处理，必须保证"老工单走老流程、新工单走新流程"的双轨并行
2. **两套平台需要整合**：虽然运营平台和精益平台都是Java工程，但两套代码的依赖版本、包结构、认证方式、配置规范都有差异，代码迁入或重写都需要逐步验证
3. **4A对接需提前安排**：4A票据透传涉及4A管理员注册应用、分配认证凭据、开通网络策略，这些跨部门协调需要前置时间
4. **下游系统对接**：精益平台对接6大外部系统、46个接口，运营平台需逐一重新对接和验证，无法批量切换
5. **数据一致性**：存量工单数据、预警规则配置、看管关系数据需按运营平台表结构迁移，迁移后需逐一校验数据完整性
6. **用户适应性**：一线运营人员已习惯精益平台的操作流程，界面和流程的变化需分阶段引入，配合培训降低切换成本

#### 2.1.4 精益平台核心流程（2套）

**流程1：预警驱动流程（被动+主动预警）**

```
创建预警任务(区公司) → 提交审批(三级主任) → 审批通过 → 预警自动触发/手动触发
→ 生成预警工单 → 自动派发至看管关系对应的网格经理/集运
→ 网格通接收执行 → 执行反馈 → 精益平台收集反馈 → 效果评估
```

派单逻辑（分包看管模式）：

精益平台采用"分包看管"派单模式，流程梳理PPT描述了大致逻辑：按客户属性（如全球通等级、政企属性等）判断派发目标。**具体派单规则和条件分支需与精益平台开发团队确认，以下仅为示意方向**：
1. 按客户属性判断（全球通等级、政企属性等）→ 派发至对应执行人
2. 按看管关系匹配 → 派发至对应的网格经理/集运
3. 执行失败或特殊情况 → 支持转派

**流程2：营销任务流程（手动创建+IOP闭环）**

```
精准营销创建客群 → 精益创建手工工单(圈选客群) → 提交审批
→ 工单派发 → 任务指派 → 分公司接收任务
→ 任务接收后跳转IOP → IOP创建活动(客群拆分/产品圈选/渠道配置)
→ 活动审批执行 → 网格通执行工单 → 执行反馈 → 效果评估
```

### 2.2 运营平台现状

运营平台（市场数智运营平台）是基于集团规范建设的市场运营平台，已具备以下核心能力框架：

**已有能力方向**：
- 指标体系：多模块指标概览+详情+区域下钻
- 运营专区：流量运营/离网维系/增量运营/家庭运营/中高端客户运营/国际业务运营
- 调度中心：6种调度类型（指标/策略/客群/客户商机/客群商机/区域攻坚）的工单闭环（⚠️ 实际调度类型以运营平台Java工程为准，此处基于原型梳理）
- 策略中心：根因库/策略库/关联关系管理
- 商机管理：分类/源/客户/客群/清洗规则/预警规则

**运营平台缺少但精益平台已成熟的能力**：预警任务配置/审批流程、工单派发执行反馈闭环、效果评估报表、看管关系管理、分包看管派单逻辑。

> **说明**：以上能力方向是基于运营平台产品设计层面梳理，运营平台实际Java工程的开发进度和已上线功能范围，需与运营平台开发团队确认。

### 2.3 两平台差异分析

| 维度 | 精益平台 | 运营平台 | 融合方向 |
|------|---------|---------|---------|

## 三、融合策略

### 3.1 融合原则

1. **以运营平台为底座**：所有融合工作在运营平台上完成，精益平台的功能迁入运营平台或在运营平台上重新实现，不迁就精益平台现有实现
2. **以集团规范为标杆**：融合后的能力按集团规范验收，精益平台的功能只是参考输入
3. **复用通路、重构能力**：精益平台已打通的外部系统通路必须复用（接口协议可参考），但业务逻辑（派单规则、预警条件等）需在运营平台上重新实现或配置
4. **分步实施、双轨并行**：每个阶段都有明确的交付物和价值体现，双轨并行确保业务连续性

### 3.2 技术路线选择

融合方案存在三种技术路线，核心分歧在于"精益平台代码迁不迁、迁哪些"，需由领导拍板选择：

#### 方案一：迁全部代码，两套调度引擎并存

**方案描述**：将精益平台全部业务代码迁入市场运营平台工程，包括调度引擎、预警规则、看管派单、报表查询、指标计算、驾驶舱视图等所有业务逻辑。迁入后的代码保持原有逻辑不变，继续运行存量流程。完全新增的需求基于市场运营平台新调度中心开发。两套调度引擎在同一工程内并存。

**迁入代码范围**：

> 以下为迁入范围的分类说明，具体模块划分由研发工程师根据两个平台的实际工程结构确定。

| 代码类别 | 包含内容 | 迁入策略 |
|---------|---------|---------|
| **调度引擎+流程代码** | 预警流程引擎、营销任务流程引擎、工单派发逻辑、看管分包派单逻辑、督办流程 | 迁入运营平台工程，初期保持原引擎独立运行 |
| **预警规则引擎代码** | 9大场景的预警规则配置、预警触发逻辑、预警任务创建逻辑 | 迁入运营平台工程，初期保持原有规则引擎运行 |
| **报表代码** | 11个报表的查询SQL/逻辑、一事一案分析、营销任务执行效果统计、驾驶舱数据聚合 | 迁入运营平台工程，初期查精益表结构，后续逐步切到运营平台表 |
| **指标计算+视图代码** | 运营驾驶舱指标计算、存量视图指标计算、合约到期/收入预测/新入网等监控指标 | 迁入运营平台工程，初期保持原有计算逻辑 |
| **外部接口对接代码** | 网格通、IOP、精准营销、在线平台、CRM、大数据平台6大系统46个接口的调用逻辑 | 迁入运营平台工程，初期复用原有接口调用逻辑 |
| **基础功能代码** | 用户认证、菜单管理、角色权限、日志审计等 | **不迁入**，使用运营平台已有基础设施 |

**改造内容**：

| 改造项 | 说明 |
|--------|------|
| 代码迁入 | 精益平台调度引擎、预警规则、看管派单、报表查询、指标计算、驾驶舱视图、外部接口对接等全部业务代码迁入运营平台工程 |
| 基础设施适配 | 迁入代码中对精益平台认证、日志、异常处理等基础设施的依赖，替换为运营平台的基础设施 |
| 前端重写 | 精益平台前端页面按运营平台前端规范重写 |
| 数据层适配 | 迁入初期保留精益平台表结构，后续逐步统一到运营平台表结构 |
| 4A票据对接 | 运营平台后端集成4A凭证申请服务，短期实现iframe免登嵌入 |
| 新调度类型扩展 | 运营平台调度中心新增预警调度(ALT)和看管调度(CUR)两种类型，供完全新增的需求使用 |

**迁入操作原则**：

> 以下为迁入操作的原则性描述，具体步骤和模块划分由研发工程师根据两个平台的实际工程结构确定。

1. **获取实际工程结构**：研发工程师梳理运营平台和精益平台各自的模块划分、包结构、分层方式
2. **确定迁入映射关系**：精益平台哪些模块迁入→对应运营平台哪个模块下，由研发工程师根据实际情况决定
3. **迁入+替换+合并**：迁移业务源码、替换基础设施依赖、合并依赖和配置、处理冲突
4. **适配认证**：迁入代码中所有4A认证相关调用改为从运营平台统一认证上下文获取用户信息
5. **前端重写**：按运营平台前端规范重写所有页面
6. **联调测试**：每个迁入场景端到端验证

**利**：

| # | 利 | 说明 |
|---|---|------|
| 1 | 存量业务代码无需重写 | 预警引擎、看管派单、报表查询、指标计算、视图渲染等全部业务逻辑是经过生产验证的代码，迁入后可直接运行 |
| 2 | 存量功能可快速恢复运行 | 代码迁入后，适配认证和基础设施即可上线，比重新开发更快 |
| 3 | 业务规则提取的工作量较小 | 不需要从代码中逐条提取业务规则再重新配置，规则已经在代码里了 |
| 4 | 下游接口调用逻辑可直接参考 | 迁入代码中保留了调用外部系统的完整逻辑 |
| 5 | 报表查询逻辑可直接复用 | 11个报表的SQL查询随代码迁入，不需要重新开发 |

**弊**：

| # | 弊 | 说明 |
|---|---|------|
| 1 | **两套调度引擎长期并存** | 老引擎跑存量流程，新引擎跑新增需求。两套引擎意味着两套派单逻辑、两套工单状态机、两套超时升级规则 |
| 2 | **"存量优化"与"新增需求"的边界模糊** | 每次需求评审都要争论走老引擎还是新引擎，管理成本高 |
| 3 | **数据模型分裂** | 老引擎工单写精益表结构，新引擎工单写运营平台表结构，报表查询需跨表合并 |
| 4 | **二次融合不可避免** | 两套引擎并存不是终态，最终还是要迁移到新引擎上，总成本=迁入+长期维护+二次融合 |
| 5 | **用户体验不统一** | 同一菜单下，老引擎和新引擎产生的工单操作方式、状态流转可能不同 |

**成本定性判断**：方案一前期投入相对可控，但需承担两套调度引擎长期并存的持续维护成本，以及后续不可避免的二次融合成本。三笔账加总，整体投入不低。

**如果选择方案一，必须明确的约束**：

1. 两套引擎并存不是终态，是过渡态，必须设定退出时间节点
2. 老引擎上只做Bug修复，不做功能新增。任何涉及新逻辑的需求一律走新引擎
3. 工单数据模型必须统一——即使调度引擎是两套，工单数据必须存在同一套表中（通过调度类型字段区分），否则报表无法统一

#### 方案1.5：部分迁代码，只迁报表/视图/评估，调度用新引擎

**方案描述**：将精益平台中**与调度引擎无耦合**的业务代码迁入运营平台工程——主要是报表查询、指标视图、效果评估等纯查询展示类代码。而调度引擎、工单管理、派单逻辑、督办等**与调度强耦合**的代码不迁入，改为在运营平台新调度中心中用规则引擎重新配置实现。全平台只保留一套调度引擎。

**核心判断依据**：哪些代码适合迁、哪些不适合迁，取决于代码与调度引擎的耦合度：

| 代码类型 | 与调度引擎的耦合度 | 迁入后能否独立运行 | 适不适合迁 |
|---------|------------------|-----------------|-----------|
| 报表查询 | 无耦合 | 能，只需适配数据源（改表名/字段名） | ✅ 适合迁 |
| 指标视图（运营驾驶舱/存量视图/事中监控） | 无耦合 | 能，同上 | ✅ 适合迁 |
| 效果评估（一事一案/营销任务执行效果） | 无耦合 | 能，同上 | ✅ 适合迁 |
| 预警规则配置 | 低耦合（保存规则，不执行调度） | 基本能，但规则触发逻辑与调度耦合 | ⚠️ 部分适合 |
| 工单管理 | **高耦合**（工单生命周期由调度引擎驱动） | 不能，必须依赖调度引擎 | ❌ 不适合迁 |
| 派单逻辑 | **高耦合**（调度引擎的核心功能） | 不能 | ❌ 不适合迁 |
| 督办管理 | **高耦合**（依赖工单体系） | 不能 | ❌ 不适合迁 |

**迁入代码范围**：

| 代码类别 | 包含内容 | 迁入策略 |
|---------|---------|---------|
| **报表代码** | 11个报表的查询SQL/逻辑、一事一案分析、营销任务执行效果统计 | 迁入运营平台工程，适配运营平台数据源 |
| **指标计算+视图代码** | 运营驾驶舱指标计算、存量视图指标计算、事中监控统计指标 | 迁入运营平台工程，适配运营平台数据源 |
| **外部接口对接代码（查询类）** | 大数据平台FTP数据获取、CRM数据查询等查询类接口 | 迁入运营平台工程，复用接口调用逻辑 |

**不迁入、需重新开发的代码**：

| 代码类别 | 包含内容 | 重新开发方式 |
|---------|---------|------------|
| **调度引擎+流程代码** | 预警流程引擎、工单派发、看管分包派单、督办流程 | 运营平台新调度中心+规则引擎重新配置实现 |
| **预警规则引擎代码** | 9大场景的预警规则配置、触发逻辑 | 提取业务规则，在新调度中心规则引擎中配置 |
| **工单管理代码** | 工单CRUD、状态流转、接收/转派/完成/回访 | 运营平台工单体系扩展（新增ALT/CUR类型） |
| **下游派发接口** | 网格通派单、IOP跳转、精准营销创建活动等 | 运营平台直接对接，复用接口协议 |

**改造内容**：

| 改造项 | 说明 |
|--------|------|
| 报表/视图/评估代码迁入 | 精益平台报表查询、指标视图、效果评估等纯查询展示类代码迁入运营平台工程 |
| 迁入代码适配数据源 | 迁入的报表/视图代码中，将精益平台表名/字段名映射到运营平台表结构 |
| 业务规则提取 | 从精益平台9大场景中提取预警规则和派单规则，形成规则配置清单 |
| 新调度中心扩展 | 运营平台调度中心新增预警调度(ALT)和看管调度(CUR)，开发规则引擎支持可配置的派单规则 |
| 9大场景规则配置 | 将提取的业务规则在新调度中心规则引擎中逐一配置 |
| 前端重写 | 所有页面按运营平台前端规范重写 |
| 4A票据对接 | 运营平台后端集成4A凭证申请服务，短期实现iframe免登嵌入 |
| 下游接口对接 | 运营平台直接对接5个外部系统，复用精益平台接口协议 |

**利**：

| # | 利 | 说明 |
|---|---|------|
| 1 | **一套调度引擎，无两套引擎并存的弊端** | 调度相关代码不迁入，全平台只有一套调度引擎，不存在边界模糊、数据模型分裂、二次融合等问题 |
| 2 | 报表/视图代码可快速复用 | 11个报表+指标视图+效果评估的查询逻辑随代码迁入，不需要重新开发，节省大量报表开发工作量 |
| 3 | 业务规则提取的工作量集中在调度层面 | 只需提取9大场景的预警规则和派单规则，报表/视图逻辑直接复用代码 |
| 4 | 数据模型统一 | 工单数据只存在运营平台一套表中，迁入的报表代码适配运营平台表结构后直接查统一表 |
| 5 | 无需二次融合 | 没有两套引擎的过渡期，调度层面一次到位 |
| 6 | 长期迭代成本最低 | 后续所有需求（含调度和报表）都在同一套体系上迭代 |

**弊**：

| # | 弊 | 说明 |
|---|---|------|
| 1 | **业务规则提取有遗漏风险** | 9大场景的预警规则和派单规则需从精益平台代码/配置/文档中提取，遗漏会导致新系统行为不一致。这是方案1.5最大的风险 |
| 2 | 报表迁入后需适配运营平台数据源 | 迁入的报表SQL查的是精益平台表结构，需逐一改为运营平台表结构。如果运营平台数据模型尚未稳定，报表代码需要反复调整 |
| 3 | 需要双轨并行验证 | 为规避规则遗漏风险，同一批预警数据同时走老系统和新系统，对比触发结果是否一致 |
| 4 | 对精益平台业务规则的文档化程度有依赖 | 需与精益平台原有开发团队配合梳理调度层面的规则 |

**成本定性判断**：方案1.5前期投入介于方案一和方案二之间——报表/视图省了重新开发的工作量，但调度层面的规则提取和配置仍需投入。长期看，一套引擎无持续维护成本，无需二次融合，整体投入较为可控。

**方案1.5的关键前提**：迁入的报表/视图代码需要适配运营平台的数据源。如果中期运营平台数据模型尚未稳定，报表代码可能需要反复调整。因此，**运营平台数据模型的稳定速度直接影响方案1.5的报表迁入效果**。

#### 方案二：不迁代码，全部重新开发

**方案描述**：不迁入精益平台代码。存量流程（9大预警场景+看管派单）的业务规则从精益平台文档和配置中提取，在市场运营平台新调度中心中用规则引擎重新配置实现。报表查询逻辑按运营平台数据模型重新开发。全平台只保留一套调度引擎。

**改造内容**：

| 改造项 | 说明 |
|--------|------|
| 业务规则提取 | 从精益平台9大场景的操作手册、预警规则配置表、看管派单逻辑中逐条提取业务规则，形成规则配置清单 |
| 新调度中心扩展 | 运营平台调度中心新增预警调度(ALT)和看管调度(CUR)两种类型，开发规则引擎支持可配置的派单规则 |
| 9大场景规则配置 | 将提取的业务规则在新调度中心的规则引擎中逐一配置 |
| 报表重新开发 | 11个报表按运营平台数据模型重新开发查询逻辑，直接查运营平台工单表 |
| 指标视图重新开发 | 运营驾驶舱、存量视图、事中监控等指标视图页面，按运营平台数据接口重新开发 |
| 前端重写 | 所有页面按运营平台前端规范重写 |
| 4A票据对接 | 运营平台后端集成4A凭证申请服务，短期实现iframe免登嵌入 |
| 下游接口对接 | 运营平台直接对接5个外部系统，复用精益平台接口协议 |

**不迁代码≠从零重写。** 需要区分：

| 精益平台能力 | 是否需要重写 | 理由 |
|------------|------------|------|
| 预警规则引擎 | **需要重新实现** | 核心逻辑是"条件匹配→触发预警"，运营平台调度中心的规则引擎可复用这个模式，但需重新实现9大场景各自的匹配条件 |
| 看管派单逻辑 | **需要重新实现** | 从精益平台现有逻辑重构为规则引擎配置项 |
| 9大场景的业务规则 | **不需要从零写，但要重新配置** | 业务规则是业务知识，不是代码。从精益平台文档和配置中提取这些规则，在新调度中心中配置为规则引擎的规则项 |
| 报表查询逻辑 | **需要重新实现** | 报表本质是SQL+数据聚合，重新实现风险低。且重写后直接查运营平台表结构，不存在跨表合并问题 |
| 指标视图逻辑 | **需要重新实现** | 本质是数据聚合+图表展示，按运营平台数据接口重新开发 |
| 下游派发接口 | **不需要重写** | 接口协议复用，运营平台重新对接调用 |
| 前端页面 | **三种方案都要重写** | 无论迁不迁代码，前端都要按运营平台规范重写 |

**利**：

| # | 利 | 说明 |
|---|---|------|
| 1 | **一套引擎，统一架构** | 所有调度类型在同一套调度中心内，一套派单逻辑、一套工单状态机、一套数据模型 |
| 2 | **数据模型统一** | 所有工单数据存在运营平台同一套表中，报表直接查一张表 |
| 3 | **无需二次融合** | 没有两套引擎并存的过渡期 |
| 4 | **对齐集团规范的路径最短** | 从第一天起就是按集团规范的架构在做 |

**弊**：

| # | 弊 | 说明 |
|---|---|------|
| 1 | **业务规则提取有遗漏风险** | 精益平台9大场景的业务规则分散在代码、配置表、操作手册中，遗漏会导致新系统行为不一致 |
| 2 | **需要更严谨的验证机制** | 必须做双轨并行验证，增加验证阶段工作量 |
| 3 | **对精益平台业务规则的文档化程度有依赖** | 需与精益平台原有开发团队配合梳理 |
| 4 | **9大场景需逐一配置和验证** | 场景数量多，整体工作量不容低估 |
| 5 | **报表/视图全部重新开发，工作量较大** | 11个报表+指标视图+效果评估全部从头开发，是方案二与方案1.5的主要差距 |

**成本定性判断**：方案二前期投入相对较高（调度规则提取+报表/视图全部重新开发），但一次到位，无需承担两套引擎并存的持续成本，也无需二次融合。

#### 三种方案核心差异对比

| 对比维度 | 方案一：全迁代码 | 方案1.5：部分迁代码 | 方案二：不迁代码 |
|---------|----------------|------------------|----------------|

#### 4A票据透传的完整流程

基于《北京移动4A系统单点登录票据申请&验证接口v1.2》，4A SSO采用WebService(SOAP)协议，核心流程为"凭证申请→URL附加Token→凭证验证→完成登录"：

```
用户登录运营平台（运营平台自身的认证流程）
  │
  ├── 用户点击左侧菜单"精益运营→预警工单管理"
  │
  ▼
运营平台后端：调用4A凭证申请服务（CreateAiuapTokenSoap）
  │  请求参数：
  │    ACCT = 运营平台接口认证用户（3DES加密，4A分配）
  │    PWD  = 运营平台接口认证密码（3DES加密，4A分配）
  │    SERVICEID = 精益平台在4A中注册的标识
  │    LOGINACCT = 当前用户在精益平台的从账号登录名
  │    TIMESTAMP = 系统时间戳
  │
  ▼
4A返回：TOKEN（单点登录票据）+ APPACCTID（4A侧从账号标识）
  │
  ▼
运营平台前端：构造iframe URL，附加Token参数
  │  iframe.src = 精益平台SSO地址 + "?token=" + TOKEN + "&appAcctId=" + APPACCTID + "&flag=1"
  │
  ▼
精益平台：接收请求，提取token参数，调用4A凭证验证服务（CheckAiuapTokenSoap）
  │  请求参数：
  │    TOKEN = 从URL中获取的凭证
  │    APPACCTID = 从URL中获取的4A侧从账号标识
  │    SERVICEID = 精益平台在4A中注册的标识
  │
  ▼
4A返回验证结果：RSP=0成功 + MAINACCTID（主账号ID）+ APPACCTID（从账号登录名）
  │
  ▼
精益平台：验证通过，初始化用户Session，展示页面（隐藏自身导航壳）
```

#### 必须前置完成的工作

| # | 工作项 | 说明 | 责任方 |
|---|--------|------|--------|
| 1 | 运营平台在4A中注册为"主访问应用系统" | 获取接口认证用户(ACCT)和密码(PWD)，用于调用CreateAiuapTokenSoap | 运营平台团队向4A管理员申请 |
| 2 | 确认精益平台在4A中注册的SERVICEID | 运营平台调用凭证申请时需要传入精益平台的SERVICEID | 精益平台团队提供 |
| 3 | 确认用户账号映射关系 | 运营平台登录的用户名，与精益平台4A从账号登录名的映射关系 | 4A管理员确认 |
| 4 | 精益平台提供SSO登录地址 | 精益平台需提供一个接收token参数的URL入口 | 精益平台团队提供 |
| 5 | 精益平台壳剥离 | 精益平台页面检测到iframe嵌入时，隐藏自身顶部导航和左侧菜单，只展示内容区 | 精益平台团队改造 |
| 6 | 网络策略开通 | 运营平台服务器需能访问4A票据服务；精益平台服务器需能访问4A验证服务 | 网络管理员开通 |
| 7 | 运营平台后端集成4A WebService调用 | 运营平台后端新增调用4A CreateAiuapTokenSoap的服务，3DES加密ACCT/PWD，解析返回的XML获取TOKEN | 运营平台后端开发 |

#### 运营平台侧需新增的后端接口

```
运营平台后端新增API：
GET /api/sso/lean-token?serviceId=精益平台SERVICEID

处理逻辑：
1. 获取当前登录用户的4A主账号/从账号信息
2. 调用4A CreateAiuapTokenSoap，传入ACCT/PWD/SERVICEID/LOGINACCT
3. 解析返回XML，提取TOKEN和APPACCTID
4. 返回给前端：{ token: "xxx", appAcctId: "xxx" }

前端使用：
const { token, appAcctId } = await fetch('/api/sso/lean-token?serviceId=LEAN_SVC_ID').then(r => r.json());
iframe.src = `http://精益平台/sso/login?token=${token}&appAcctId=${appAcctId}&flag=1`;
```

#### 4A票据透传关键注意事项

1. **Token时效性**：4A生成的TOKEN有时效限制（通常几分钟），运营平台应在用户点击菜单时实时申请Token，不能缓存Token复用
2. **3DES加密**：ACCT和PWD字段必须用3DES加密传输，加密密钥由4A分配
3. **SOAP协议**：4A接口是WebService(SOAP)协议，运营平台后端需使用SOAP客户端（如Apache CXF、Spring WebServiceTemplate）调用
4. **XML解析**：4A返回的是XML格式报文，需正确解析提取TOKEN/RSP/APPACCTID等字段
5. **错误处理**：4A凭证申请失败时（RSP≠0），运营平台应给用户友好提示，而非显示空白iframe
6. **审计日志**：4A要求接入后应用日志也要接入，运营平台需将用户通过4A登录的操作日志按4A规范上报

#### iframe嵌入的其他技术问题

1. **高度自适应**：iframe加载后监听精益平台页面高度变化，动态调整iframe高度，避免出现双滚动条
2. **面包屑导航**：iframe外层统一包装运营平台的面包屑导航和操作工具栏，让用户感知仍是在同一个平台内操作
3. **壳剥离**：精益平台页面检测`window.top !== window.self`时隐藏自身导航，或通过URL参数控制

#### 4.3.4 双轨并行期数据一致性策略

中期12月进入双轨并行验证阶段，需明确数据一致性规则：

| 场景 | 策略 | 说明 |
|------|------|------|
| 新增预警 | **只走运营平台** | 设定一个"切换日期"，该日期之后所有预警触发只推运营平台，精益平台不再产生新工单 |
| 在途工单 | **精益平台内自然收尾** | 切换日期前已派发的精益平台工单，在精益平台内处理完毕，不迁移中间状态 |
| 两边工单状态 | **不需要同步** | 新工单在运营平台、旧工单在精益平台，互不干扰。用户在运营平台看新工单，精益平台看旧工单 |
| 双轨并行期 | **约2-4周** | 等精益平台在途工单基本收尾后，精益平台进入只读模式 |

**关键决策点**：切换日期的选择——建议选在月末（当月预警任务已完成当轮触发），避免在预警触发过程中切换。

#### 4.3.5 回退方案

融合方案采用分步实施，每一步都可以独立回退：

| 阶段 | 回退触发条件 | 回退方式 | 回退影响 |
|------|------------|---------|---------|
| 短期（iframe集成） | 4A票据透传故障导致用户无法访问精益页面 | 运营平台"精益运营"菜单一键下线（隐藏菜单项），用户恢复直接访问精益平台 | 零影响，精益平台本身未做任何改动 |
| 中期（预警模块上线后） | 某场景规则遗漏导致重大业务问题 | 将该场景的预警触发切回推精益平台，运营平台仅保留其他场景 | 仅影响问题场景，其他场景不受影响 |
| 中期（全面切换后） | 运营平台整体不可用 | 全部预警切回精益平台（精益平台保持只收尾状态期间仍可临时接收新预警） | 需精益平台配合临时恢复接收 |

**核心原则**：精益平台在中期结束前保持可运行状态，不提前停机，作为天然的回退保障。

**关键判断**：

1. 7个报表（#3-#8, #10）依赖预警引擎数据，必须等预警模块就绪后才能实现原生报表

4. 方案一：迁入报表查询逻辑代码，前端重写，但需注意查询的是精益平台表结构还是运营平台表结构

#### 5.2.2 调度类型扩展方案

精益平台5类工单类型无法直接映射到运营平台现有6种调度类型。建议新增2种专用调度类型：

| 新增调度类型 | 前缀 | 覆盖精益平台场景 | 说明 |
|------------|------|----------------|------|
| **预警调度** | ALT | 营销类+提醒类+到期类 | 涵盖9大预警场景中由预警自动触发的工单。到期类本质是时间维度预警，合并进来 |
| **看管调度** | CUR | 分包看管派单 | 涵盖精益平台的"分包看管"逻辑：全球通等级判断→政企判断→网格经理/地市集运 |

**为什么不是5种而是2种？**

1. **效果类不需要调度**：效果评估是定时统计，不产生工单，直接在效果评估模块中展示
2. **到期类合并到预警调度**：到期提醒本质是时间维度预警，"套餐还有30天到期"和"客户消费异动"在系统处理上没有本质区别
3. **任务类已被运营平台覆盖**：手动创建的营销任务=策略调度；IOP回传任务=客群调度

#### 5.2.6 派单规则引擎设计

精益平台当前派单逻辑为分包看管模式，具体实现方式（硬编码还是配置化）需与精益平台开发团队确认。

运营平台派单引擎设计原则：

| 设计原则 | 说明 |
|---------|------|
| 配置化 | 派单规则通过配置而非硬编码实现，支持运营人员在界面上配置派发条件、执行渠道、超时升级等 |
| 规则组 | 每个预警场景对应一组派单规则，规则组内按优先级排序 |
| 条件+动作 | 每条规则由"匹配条件"和"执行动作"组成，如"预警场景=携转挽留 AND 客户等级=金卡 → 派发至10088" |
| 支持转派 | 执行失败或特殊情况支持转派至其他执行人 |
| 可扩展 | 新增场景时零代码配置新规则组 |

> **说明**：派单规则引擎的具体数据结构、配置界面、运行机制需在实施阶段结合运营平台调度中心架构设计确定。

#### 5.2.7 下游派发接口复用

运营平台调度中心直接对接5个外部系统，复用精益平台接口协议：

| 下游系统 | 复用接口 | 复用说明 |
|---------|---------|---------|
| 网格通（新大陆） | JY-01~07 + 4个FTP | 工单派发/执行反馈/督办/分派关系/活动办理，接口协议复用，运营平台重新对接 |
| IOP | JY-08~09 | 营销活动同步/执行节点反馈 |
| 精准营销 | JY-05/JY-23/JY-24 | 客群发布通知/客群查询/客群推送 |
| 在线平台(10086/10088) | JY-21/JY-22 | 携转任务下发/结果查询 |
| CRM | JY-14/JY-15 | 用户办理数据同步/携转用户同步 |

**"运营平台重新对接"的含义**：

1. 接口协议复用：请求/响应格式、字段定义、编码规则等直接参考精益平台接口文档
2. 调用方变更：运营平台后端调用，不再经精益平台中转
3. 认证方式适配：运营平台需获取各外部系统的调用凭证（AppKey/Secret/Token）
4. 接口版本确认：需与各外部系统确认当前接口版本是否仍是最新版
5. FTP文件接口：5个FTP文件传输接口涉及文件格式、传输频率、对账机制，逐一验证

**为什么运营平台要直接对接而不通过精益平台中转？**

因为中转意味着依赖链更长（运营→精益→网格通），任何一环故障影响全链路；且精益平台的中转接口字段与集团调度类型不一致，中转时还需做字段转换，增加复杂度。直接对接虽然初期工作量大，但长期维护成本更低。

## 七、总结

本融合方案的核心逻辑是：

1. **短期（8月）**：用4A票据透传+iframe嵌入解决"登录两个系统"的痛点，精益平台零改动即可集成
2. **中期（9-12月）**：将精益平台的核心能力融合至运营平台——预警中心/执行监控/效果评估/报表，运营平台直接对接外部系统
3. **长期（2027Q1+）**：运营平台完全替代精益平台——补齐独有能力+集团规范新能力+精益归档下线

三种技术路线的选择：

- **方案一（全迁代码）**：前期投入相对最低，但两套调度引擎并存带来长期维护成本和二次融合成本，长期总成本最高
- **方案1.5（部分迁代码，推荐）**：报表/视图/评估迁入复用，调度用新引擎重新配置。既避免了两套引擎并存的弊端，又节省了报表重新开发的工作量。前期投入中等，长期总成本较低
- **方案二（不迁代码）**：前期投入相对最高（调度+报表全部重新开发），但一次到位，无持续维护成本和二次融合成本

每一步都有明确的交付物和价值体现，每一步都以前一步为基础，不存在"空中楼阁"式的规划。
