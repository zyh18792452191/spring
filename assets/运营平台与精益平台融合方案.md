#### 精益平台核心流程（2套）

**流程1：预警驱动流程（被动+主动预警）**

```
创建预警任务(区公司) → 提交审批(三级主任) → 审批通过 → 预警自动触发/手动触发
→ 生成预警工单 → 自动派发至看管关系对应的网格经理/集运
→ 网格通接收执行 → 执行反馈 → 精益平台收集反馈 → 效果评估
```

派单逻辑（分包看管模式）：
1. 判断是否全球通用户 → 是 → 判断是否白金/钻/金卡 → 是 → 10088执行 / 否 → 客户经理执行
2. 判断是否政企客户关键人 → 是 → 客户经理执行
3. 以上都不是 → 网格经理/地市集运执行
4. 执行过程中如用户有宽带+要求上门 → 可转派装维

**流程2：营销任务流程（手动创建+IOP闭环）**

```
精准营销创建客群 → 精益创建手工工单(圈选客群) → 提交审批
→ 工单派发 → 任务指派 → 分公司接收任务
→ 任务接收后跳转IOP → IOP创建活动(客群拆分/产品圈选/渠道配置)
→ 活动审批执行 → 网格通执行工单 → 执行反馈 → 效果评估
```

## 二、背景与目标

### 2.1 融合背景

**业务痛点**：当前新疆移动市场运营人员需要在两套系统之间频繁切换——
- 精益平台处理预警工单的创建、审批、派发、执行反馈
- 运营平台查看指标数据、进行商机分析、区域攻坚调度

两套系统界面风格不同、登录入口不同、数据不互通，导致：
1. 操作效率低：同一业务需在两个系统分别操作
2. 数据不一致：指标数据在运营平台看，工单执行在精益平台看，无法形成"指标→预警→调度→执行→效果"的完整闭环
3. 学习成本高：新员工需要学习两套系统的操作逻辑

**政策驱动**：集团要求统一部署"XX移动市场运营平台"标准版本，精益平台的命名、菜单结构、界面框架均与集团规范不一致，需要按集团规范进行统一。

### 2.2 核心目标

**将运营平台作为统一入口，分阶段将精益平台的核心能力融合至运营平台，最终实现"一个平台、一套界面、一次登录、闭环运营"。**

### 2.3 专家判断——对用户方案的逐条审视与建议

#### 审视1：短期"页面集成"方案的技术路径

用户原文："优先进行页面集成，将核心使用页面（如预警工单）集成至新平台"

**我的判断**：页面集成有三种技术路径，需根据页面特性选择，不能一刀切用iframe——

| 技术路径 | 适用场景 | 优势 | 劣势 |
|---------|---------|------|------|
| **A. iframe嵌入** | 只读展示类页面（驾驶舱、报表、监控看板） | 实现快，不影响精益原有功能 | 双滚动条、样式不一致、弹窗被裁剪 |
| **B. 深度链接+SSO** | 复杂交互页面（预警配置、工单审批、IOP跳转） | 完整保留精益交互体验，不受iframe限制 | 仍在两个系统，但免登录跳转 |
| **C. 原生重构** | 高频核心页面（预警工单管理、我的营销任务） | 统一体验、数据互通、可扩展 | 开发量大 |

**我的建议**：短期（8月）采用**A+B混合策略**——
- 4个P0高频交互页面（预警任务管理、预警工单管理、我的营销任务、一线任务执行监控）采用**B方案（深度链接+SSO）**，在运营平台菜单中配置入口，点击后新标签页打开精益平台对应页面，通过4A SSO透传实现免登录
- 4个P0展示类页面（运营驾驶舱、效果评估）采用**A方案（iframe嵌入）**，在运营平台中以iframe形式嵌入
- 其余5个P1/P2页面暂不集成，仍在精益平台操作

**不建议8月全部用iframe的原因**：预警任务配置页有复杂的多步表单（预警规则配置→过滤对象选择→工单派发预览→审批人选择），iframe中的弹窗、下拉、文件上传等交互极易出现兼容性问题，强行iframe化反而增加排障成本，不如深度链接来得稳。

#### 审视2：中期"流程、报表及数据迁移"的可行性

用户原文："推进流程、报表及数据的迁移与整合"

**我的判断**：9-12月四个月完成全部流程+报表+数据迁移**过于乐观**。理由如下：

1. **流程迁移量被低估**：精益平台有7大预警场景×5种工单类型×2套核心流程，每个场景的派单逻辑不同（携转先10086后网格、全球通看等级分流、热线商机直接网格），这些硬编码在精益平台后端的业务规则，不能简单"搬迁"，必须在新平台重新实现并逐一验证
2. **报表迁移不只是"搬页面"**：11个常用报表的背后是大数据平台的5个FTP文件接口（一事一案到期用户监控、存量拍照价值客户清单、网格区域层级信息、合约专题看板、用户网格归属），每个接口的数据字段、更新频率、取数口径都需要重新对接
3. **数据迁移需要双轨并行期**：新平台上线后精益平台不能立即下线，需要至少1个月的双轨并行验证

**我的建议**：中期目标拆分为两步——
- **9-10月**：完成4个P0页面的原生重构（预警工单管理、效果评估、一线执行监控、我的营销任务），实现运营平台直接调用精益平台后端API，前端体验统一
- **11-12月**：完成6种调度类型接口扩展（P0级）+ 11个报表迁移 + 精益后端API逐步切换至运营平台直接对接大数据

**为什么不在顶部导航栏单独加"精益平台"入口？**
因为运营平台的定位是"统一入口"，如果单独加一个与"运营专区"平级的入口，等于在界面上承认"这是两个系统"，不利于融合的体感。放在"运营专区"下作为子菜单，用户感知是"运营平台的一个子模块"，而非"另一个系统"。

##### 改造项2：SSO统一认证透传

**实现方式**：运营平台通过4A SSO Token透传，用户从运营平台点击精益运营菜单时，自动携带4A Token跳转到精益平台，精益平台验证Token后免登录进入。

**技术方案**：
1. 运营平台登录时获取4A Token
2. 点击"精益运营"菜单时，在URL中携带4A Token参数
3. 精益平台新增Token验证拦截器，验证通过后自动创建Session
4. Token有效期与运营平台Session同步，避免单侧过期导致另一侧失效

**需要精益平台侧配合**：新增Token验证接口，约0.5人天工作量。

##### 改造项3：iframe页面样式适配

对于采用iframe嵌入的4个展示类页面（运营驾驶舱、执行监控、效果评估），需要：
1. 隐藏精益平台的顶部导航栏和左侧菜单栏（通过URL参数控制）
2. 精益平台页面body背景色适配运营平台主题色（当前运营平台为浅灰背景，精益平台为白色背景）
3. iframe高度自适应内容，避免双滚动条
4. 精益平台弹窗z-index调整为高于运营平台层级

**需要精益平台侧配合**：新增"嵌入模式"URL参数支持，约1人天工作量。

##### 改造项4：深度链接跳转优化

对于采用深度链接的3个交互类页面（预警任务管理、预警工单管理、我的营销任务），需要：
1. 新标签页打开时自动最大化
2. 页面标题显示"[运营平台] 预警任务管理"，让用户知道来源
3. 任务完成后提供"返回运营平台"按钮（精益平台页面顶部临时增加返回按钮）

**需要精益平台侧配合**：嵌入模式下增加返回按钮，约0.5人天工作量。

|-----------|-------|-----------|

| 网格通：扩展执行反馈接口增加转化效果字段 | 网格通团队 | 2人天 |

| IOP：扩展执行反馈接口增加效果评估维度 | IOP团队 | 2人天 |

**运营平台侧**：新增6种调度类型的工单创建/派发/回单接口，直接对接网格通和IOP（不经由精益平台中转）。

**为什么运营平台要直接对接网格通/IOP，而不是通过精益平台中转？**
因为中转意味着依赖链更长（运营→精益→网格通），任何一环故障影响全链路；且精益平台的中转接口字段与集团6种调度类型不一致，中转时还需要做字段转换，增加复杂度。直接对接虽然初期工作量大，但长期维护成本更低。

### 4.2 流程整合

**挑战描述**：现有流程复杂，直接迁移难度高。

**具体分析**：

#### 4.2.1 两套流程体系的差异

| 维度 | 精益平台 | 运营平台（集团规范） | 差异 |
|------|---------|-------------------|------|
| 调度类型 | 预警工单（1种，按场景细分） | 6种调度类型（指标/策略/客群/客户商机/客群商机/区域攻坚） | 精益的"预警工单"需映射到运营平台的多种调度类型 |
| 预警触发 | 5类预警类型（营销/任务/提醒/效果/到期） | 指标监控预警（运营平台指标树驱动） | 分类逻辑完全不同 |
| 派单逻辑 | 硬编码if-else（按客户属性路由） | 规则引擎（可配置的派单规则） | 精益的硬编码需抽象为规则 |
| 工单结构 | 单层工单 | 主工单+子单（6种调度类型各有不同字段结构） | 运营平台工单结构更复杂 |
| 审批流程 | 单级审批（三级主任） | 可配置多级审批 | 运营平台更灵活 |
| 效果评估 | 按场景的固定报表 | 6种调度类型×5个评估维度的矩阵 | 运营平台评估更体系化 |

#### 4.2.2 流程映射方案

**预警工单 → 多种调度类型的映射**：

| 精益预警场景 | 映射到运营平台调度类型 | 映射逻辑 |
|------------|---------------------|---------|
| 携转挽留 | 客户商机调度 | 单客户维度触发，适合客户商机调度 |
| 宽带离网 | 客群调度 | 批量客群触发，适合客群调度 |
| 全球通离网 | 客户商机调度+客群调度 | 单客户触发走客户商机，批量触发走客群调度 |
| 全球通投诉问题 | 客户商机调度 | 单客户触发 |
| 异动客户修复 | 客群调度 | 批量客群触发 |
| 热线商机 | 客户商机调度 | 单客户触发 |
| 全球通离网原因追溯 | 指标调度 | 按指标异动触发 |
| 全球通停机客户赢回 | 客户商机调度+客群调度 | 单客户+批量混合 |

**不是所有精益流程都需要1:1映射**。比如"提醒类预警"和"效果类预警"在运营平台被指标监控预警+效果评估模块替代，不再作为独立的预警类型存在。

#### 4.2.3 派单引擎设计

精益平台当前派单逻辑（以分包看管模式为例）：
```
IF 全球通用户:
    IF 白金/钻/金卡: → 10088执行
    ELSE: → 客户经理执行
ELIF 政企客户关键人: → 客户经理执行
ELSE: → 网格经理/地市集运执行
```

运营平台派单引擎设计：
```yaml
规则组: 携转挽留派单规则
优先级: 1
条件:
  - 调度类型 = 客户商机调度
  - 预警场景 = 携转挽留
执行:
  - 步骤1: 派发至10086在线渠道
  - 步骤2: 在线维系失败 → 按看管关系转派网格经理
  - 步骤3: 网格维系失败且为政企客户 → 转派客户经理
  - 步骤4: 客户有装维需求 → 转派装维
超时: 48小时未反馈自动督办
```

这种配置化的派单规则，比精益平台的硬编码if-else更灵活，也支持后续新增场景时零代码配置。

## 七、关于分步实施的理由说明

王主任要求"如果无法一步到位，可以分步实施，但要说明清楚原因和理由"。以下逐一说明：

### 为什么不能一步到位？

**理由1：两套平台的技术栈完全不同**
- 精益平台：Java后端+传统JSP/Vue前端，部署在独立服务器
- 运营平台：Next.js 16全栈+React 19+shadcn/ui，部署在容器化环境
- 代码层面无法"合并"，只能"融合"（运营平台重新实现精益平台的能力）

**理由2：数据通路无法一键切换**
- 精益平台与6大外部系统有46个接口，其中5个是FTP文件接口
- 运营平台需要逐一重新对接这些接口，每个接口都需要确认数据口径、测试联调
- 在所有接口未验证通过前，不能切断精益平台的数据通路

**理由3：业务连续性不能中断**
- 精益平台日均处理数千条预警工单，涉及携转挽留等实时性要求高的场景
- 不能在运营平台能力未验证前就关闭精益平台
- 必须有双轨并行期确保业务不受影响

**理由4：用户需要适应期**
- 区公司和分公司业务人员已习惯精益平台的操作流程
- 新平台功能更复杂（6种调度类型 vs 1种预警工单），需要培训和适应
- 分步实施让用户有时间逐步接受

### 为什么选择"短-中-长"三阶段而非"两阶段"？

如果只有"短期集成"和"全面融合"两阶段：
- 短期集成后直接跳到全面融合，中间没有验证缓冲期
- 全面融合如果失败，没有回退路径（精益平台可能已经部分下线）
- 三阶段的好处是中期结束时运营平台已具备核心能力，长期阶段只做"收尾"，风险可控

## 八、总结

本融合方案的核心逻辑是：

1. **短期（8月）**：用最小代价解决"登录两个系统"的痛点——SSO透传+页面集成，精益平台零改动
2. **中期（9-12月）**：将精益平台的核心能力"翻译"为运营平台原生能力——预警中心/执行监控/效果评估，直接对接外部系统
3. **长期（2026Q1+）**：运营平台完全替代精益平台——补齐独有能力+集团规范新能力+精益归档下线

每一步都有明确的交付物和价值体现，每一步都以前一步为基础，不存在"空中楼阁"式的规划。
